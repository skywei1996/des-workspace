# DES 在数字员工对话中接入知识库说明

## 1. 文档目的

本文档用于说明 DES 中“数字员工接入知识库”的整体实现目标、关键链路、接口边界和编码约束，重点关注知识库如何从后台配置能力变成数字员工在实际对话中可调用、可引用、可返回依据的回答能力。

本文档覆盖的核心范围包括：

- 在 DES 数字员工创建和编辑流程中，支持选择可用知识库，并明确可选范围为至少包含 1 篇切块成功文档的知识库。
- 在用户与数字员工对话时，支持基于该数字员工已绑定的知识库发起检索，并将检索结果作为回答上下文。
- 在数字员工执行 plan 过程中，支持在某一个或多个步骤中按需调用知识库内容，而不是仅在最终回答阶段统一检索。
- 知识检索、召回和重排能力统一通过火山引擎接口完成，再将处理后的结果交给 agent 组织语言并生成最终回复。

最终目标是让数字员工具备稳定的“带知识回答”能力，即：前台可配置、对话中可检索、执行过程中可引用、回复结果可追溯到知识来源。

本文档基于当前代码结构和下一步实现目标整理，既描述现状，也给出后续代码编写时必须遵守的规范。

## 2. 相关接口说明

火山引擎知识检索接口：

- https://www.volcengine.com/docs/84313/1350012?lang=zh

火山引擎 rerank 接口：

- https://www.volcengine.com/docs/84313/1254474?lang=zh

DES 当前知识库检索调试接口：

- `POST /knowledge-bases/{knowledge_base_id}/search`

说明：

当前知识库底层已经支持对单个知识库发起检索，但数字员工对话链路尚未完整接入“员工已绑定知识库 -> 自动检索 -> 注入回答上下文 -> 返回引用依据”的闭环能力。本文件的主要作用就是定义这个闭环的实现规范。

## 3. 当前实现状态与目标差距

### 3.1 已有能力

当前代码中，以下基础能力已经存在：

- `AIEmployee` 数据模型已经具备 `knowledge_ids` 字段。
- 数字员工创建/编辑接口已经支持保存 `knowledge_ids`。
- 数字员工前端配置页已经支持选择知识库。
- 知识库管理模块已经支持文档上传、状态同步、切片回传、原文预览和搜索调试。
- 火山引擎知识库检索能力已经通过 `backend/app/services/volcengine_knowledge_base.py` 接入。

### 3.2 当前缺口

当前对话主链路中，知识库还没有真正进入数字员工运行时上下文。具体表现为：

- `mcp_server.py` 中 direct response 流程尚未根据 `employee.knowledge_ids` 自动加载知识库上下文。
- plan 生成和 plan 执行流程中，还没有把“是否需要调用知识库”作为显式能力接入步骤设计。
- 当前 `employee_context` 只包含 persona、skills、workflow 等内容，不包含知识库摘要、检索结果或引用材料。
- 对话结果尚未形成统一的“引用来源”返回结构。

### 3.3 本文定义的目标状态

实现完成后，应达到以下标准：

1. 数字员工创建和编辑时，可稳定绑定一个或多个有效知识库。
2. direct response 模式下，数字员工可按需自动检索所绑定知识库并据此回答。
3. plan 模式下，planner 可以决定某个步骤是否调用知识库，execution 阶段可执行该决定。
4. 回答结果可以携带清晰的知识来源，包括知识库、文档、切片等信息。
5. 整条链路应保持统一实现，避免在不同入口各自拼装一套检索逻辑。

## 4. 当前整体架构

当前“数字员工对话接入知识库”链路可以拆成 5 层：

1. DES 数字员工前端配置页
2. DES 数字员工后端数据模型与员工管理接口
3. DES 对话与 plan 执行入口
4. DES 知识库服务层
5. 火山引擎知识库检索与重排能力

目标核心流程如下：

```text
在数字员工配置页选择知识库
  -> 保存到 AIEmployee.knowledge_ids

用户向数字员工发起对话
  -> DES 后端识别当前 employee_id
  -> 读取 employee.knowledge_ids
  -> 过滤出可用知识库
  -> 按用户问题发起知识检索与重排
  -> 将检索结果作为上下文注入 direct response 或 plan execution
  -> agent 基于检索结果组织最终回答
  -> 返回回答正文 + 引用来源

如果进入 plan 模式
  -> planner 生成 plan_steps
  -> 某些 step 可标记为需要知识库检索
  -> execution 按 step 调用知识库检索
  -> 汇总各步骤结果并输出最终答案
```

## 5. 主要数据模型

### 5.1 `ai_employees`

定义位置：

- `backend/app/models.py`
- `backend/app/schemas.py`

当前关键字段：

- `id`: 数字员工 ID
- `name`: 数字员工名称
- `role_title`: 职责标题
- `description`: 员工描述
- `persona_prompt`: 人设提示词
- `tool_ids`: 绑定的技能列表
- `workflow_ids`: 绑定的工作流列表
- `knowledge_ids`: 绑定的知识库 ID 列表
- `action_guide`: 员工操作指南与偏好配置

约束说明：

- `knowledge_ids` 必须是 DES 本地知识库 ID 列表，不允许直接保存火山远端 `resource_id`。
- `knowledge_ids` 中允许保存历史遗留 ID，但运行时必须做有效性过滤，不能盲信前端传值。

### 5.2 `knowledge_bases`

定义位置：

- `backend/app/models.py`

当前关键字段：

- `id`: DES 本地知识库 ID
- `name`: 知识库名称
- `remote_resource_id`: 火山远端知识库 ID
- `remote_collection_name`: 火山知识库名称
- `sync_status`: 知识库同步状态
- `documents`: 本地文档列表

运行时关注点：

- 只有远端绑定有效、并且存在至少 1 篇 `processed` 文档的知识库，才应视为“可用于数字员工对话”。

### 5.3 `knowledge_documents`

定义位置：

- `backend/app/models.py`

当前关键字段：

- `id`: 本地文档 ID
- `knowledge_base_id`: 所属知识库
- `remote_doc_id`: 火山文档 ID
- `status`: `waiting / processing / processed / failed`
- `chunks`: 已同步回本地的切片列表
- `source_url`: 原始文件地址

对话接入时的意义：

- 数字员工绑定知识库时，不直接使用文档或切片表做检索，而是通过知识库维度发起检索；文档和切片主要用于筛选知识库是否可用、以及回答后引用来源的展示。

## 6. 数字员工绑定知识库流程

### 6.1 前端配置入口

当前前端实现位置：

- `react-des/src/pages/AddSiliconWorker.jsx`

当前已存在的行为：

- 数字员工创建/编辑页支持打开知识库选择弹窗。
- 弹窗中已经提示“Only knowledge bases with processed content can be assigned to a digital employee.”
- 提交员工配置时会将选中的知识库写入 `knowledge_ids`。

### 6.2 后端保存入口

当前后端入口：

- `POST /ai-employees/`
- `PUT /ai-employees/{employee_id}`

当前实现位置：

- `backend/app/routers/employees.py`

当前行为：

1. 前端提交 `knowledge_ids`
2. 后端 `_normalize_employee_payload(...)` 将其标准化为列表
3. 写入 `AIEmployee.knowledge_ids`

### 6.3 后续必须补充的校验规则

为了保证后续对话链路稳定，员工保存时建议增加以下校验：

1. `knowledge_ids` 中的每一个 ID 必须存在于本地 `knowledge_bases` 表。
2. 每个候选知识库必须满足：
	- `remote_resource_id` 存在
	- 至少存在 1 篇 `processed` 文档
3. 不满足条件的知识库不能保存到员工配置，或者至少要返回 warning 并在 UI 中标明不可用原因。

规范建议：

- 前端负责过滤和提示。
- 后端负责最终强校验。
- 不允许只靠前端约束知识库可用性。

## 7. 对话接入主链路

### 7.1 当前 direct response 入口

当前实现位置：

- `backend/app/mcp_server.py`

当前关键函数：

- `_answer_direct_for_employee(...)`
- `_resolve_employee_id_for_chat(...)`
- `_build_employee_context(...)`
- `_build_direct_response_prompt(...)`
- `_run_direct_agent(...)`

当前 direct response 流程：

1. 根据 `chat_id` 或显式 `employee_id` 找到数字员工。
2. 读取员工技能和 workflow。
3. 构建 `employee_context`。
4. 结合 `build_effective_user_request(...)` 生成 prompt。
5. 调用 execution agent 直接回答。

### 7.2 对话接入知识库后的目标流程

目标流程应调整为：

1. 解析当前 `employee_id`
2. 读取 `employee.knowledge_ids`
3. 加载这些知识库并过滤出“可用知识库”
4. 基于用户问题发起知识检索
5. 将检索命中的知识摘要、切片内容、来源信息注入 prompt
6. agent 在回答中使用这些内容
7. 同时返回结构化引用信息供前端展示

规范要求：

- direct response 中的知识检索必须在进入 `_run_direct_agent(...)` 之前完成。
- 不允许让模型“猜测是否有知识库”，必须由后端明确注入知识上下文。
- 如果没有命中结果，应明确告诉 agent“本次未命中知识库内容”，而不是 silently fallback。

## 8. plan 模式接入主链路

### 8.1 当前 plan 相关入口

当前实现位置：

- `backend/app/mcp_server.py`

当前关键入口：

- `POST /plan`
- `POST /execute_plan`

当前关键函数：

- `_build_plan_steps(...)`
- `_assign_skills_by_scene(...)`
- `_coerce_execute_plan_steps(...)`
- `_format_execute_plan_prompt(...)`

### 8.2 目标行为

plan 模式接入知识库后，应支持两种方式：

1. 自动知识检索模式
	- planner 识别问题需要资料支撑时，自动生成知识检索相关步骤。

2. 显式知识检索步骤模式
	- 某个 `plan_step` 明确标记需要调用知识库。

### 8.3 推荐的步骤设计规范

建议为 `PlanStep` 增加以下可选字段：

- `use_knowledge`: 是否需要知识检索
- `knowledge_ids`: 本步骤允许使用的知识库范围
- `knowledge_query`: 本步骤用于检索的子问题
- `knowledge_top_k`: 本步骤召回条数

推荐行为：

- 如果 step 明确要求查找事实、总结材料、引用原文、比对方案、归纳依据，则默认 `use_knowledge=true`。
- 如果 step 是纯工具执行、纯生成、纯格式整理，则不应无意义地发起知识检索。

### 8.4 plan 执行时的规范

执行 `execute_plan` 时：

1. 先解析 `plan_steps`
2. 对每个 `use_knowledge=true` 的步骤单独发起检索
3. 将该步骤的检索结果写入步骤级上下文
4. 再执行该步骤的 agent 推理或工具调用

重要约束：

- 不允许把所有知识检索都塞到 plan 最后一步。
- 不允许 planner 生成了知识步骤，但 execution 阶段完全忽略。

## 9. 知识库可用性判定规范

数字员工运行时，对知识库必须执行统一的可用性过滤。推荐标准如下：

### 9.1 可用知识库条件

一个知识库只有在同时满足以下条件时才可进入运行时：

1. 本地知识库存在。
2. `remote_resource_id` 非空。
3. `sync_status` 不属于显式错误状态。
4. 至少存在 1 篇 `processed` 文档。

### 9.2 不可用知识库处理方式

如果员工绑定了不可用知识库：

- 运行时应忽略该知识库。
- 应记录日志，说明被忽略的原因。
- 如全部知识库都不可用，则 direct/plan 流程必须进入“无知识库上下文”分支。

### 9.3 不允许的实现方式

- 不允许仅凭 `knowledge_ids` 非空就发起检索。
- 不允许将 `waiting / processing / failed` 文档的知识库视为已准备好。

## 10. 检索与重排链路规范

### 10.1 推荐调用方式

数字员工对话链路不应直接重复拼装火山请求参数，建议通过统一服务层进行：

1. 先走 DES 内部知识库服务层
2. 由服务层调用火山检索和重排能力
3. 返回统一结构给 direct response / plan execution

推荐封装位置：

- 新增服务文件，例如 `backend/app/services/employee_knowledge_service.py`

### 10.2 建议服务职责

该服务建议提供以下能力：

- `resolve_employee_knowledge_bases(employee, db)`
- `filter_effective_knowledge_bases(knowledge_bases)`
- `search_employee_knowledge(employee, query, db, ...)`
- `format_knowledge_context_for_prompt(search_results)`
- `format_knowledge_citations(search_results)`

### 10.3 多知识库检索策略

建议采用以下策略：

1. 对员工绑定的每个知识库分别发起检索。
2. 合并返回结果。
3. 按 rerank 分数统一排序。
4. 截断到最终可注入的条数。

规范要求：

- 合并后的排序逻辑必须统一，不能前端一套、plan 一套、direct 一套。
- 至少保留 `knowledge_base_id / knowledge_base_name / document_id / document_name / content / score / rerank_score / chunk_id / chunk_type` 等字段。

## 11. 对 prompt 注入知识上下文的规范

### 11.1 注入原则

知识检索结果进入 prompt 时，必须结构化，而不是简单粗暴拼接全文。

推荐格式：

```text
Knowledge Base Context:
1. [知识库: sales][文档: xxx.pdf][切片: 12][分数: 0.87]
	内容: ...

2. [知识库: hr_policy][文档: yyy.docx][切片: 3][分数: 0.82]
	内容: ...
```

### 11.2 注入位置

建议在 `_build_employee_context(...)` 之外新增一个专门的 knowledge context 构造函数，不要把知识检索逻辑直接写死在 persona context 里。

推荐分层：

- `employee_context`: 人设、技能、workflow、操作指南
- `knowledge_context`: 检索结果和引用依据
- `effective_user_request`: 对用户问题的整理结果

### 11.3 prompt 约束

prompt 中应明确要求 agent：

- 优先基于知识上下文回答
- 如果知识上下文不足，应明确说明“未在知识库中找到充分依据”
- 不允许伪造知识来源
- 如果回答引用了知识内容，应尽量保持与切片原文语义一致

## 12. 回答结果与引用返回规范

### 12.1 目标

回答结果不仅要有正文，还要支持前端显示“答案引用了哪些知识来源”。

### 12.2 推荐返回结构

建议在当前 chat 或 execute 返回结构中增加：

- `knowledge_hits`: 实际参与回答的命中片段

建议单条命中至少包含：

- `knowledge_base_id`
- `knowledge_base_name`
- `document_id`
- `document_name`
- `chunk_id`
- `chunk_type`
- `content`
- `score`
- `rerank_score`

### 12.3 使用原则

- direct response 和 plan execution 的返回结构应一致。
- 如果本轮未使用知识库，则 `knowledge_hits` 返回空数组，而不是省略字段。

## 14. 错误处理与降级规范

必须定义以下降级路径：

### 14.1 员工未绑定知识库

- 不报错
- 直接按无知识库上下文执行

### 14.2 员工绑定的知识库全部不可用

- 不报错
- 记录 warning
- 回答走普通 direct/plan 流程

### 14.3 检索接口失败

- 单个知识库失败时，不影响其他知识库检索
- 所有知识库都失败时，记录 error，并进入无知识上下文降级流程

### 14.4 无命中结果

- 允许正常回答
- 但 prompt 中必须明确“本轮未检索到相关知识依据”

## 15. 编码规范与实现原则

为了保证后续代码实现一致，必须遵守以下原则：

### 15.1 单一服务入口

知识库解析、过滤、检索、重排、引用格式化必须走统一服务层，不允许在：

- `mcp_server.py`
- `workflow_service.py`
- 单独路由

中各写一套。

### 15.2 不直接依赖前端筛选

前端可以限制只能选“processed”知识库，但后端仍必须重复校验。

### 15.3 不把知识库信息硬编码进 prompt 模板

知识库上下文必须通过结构化函数生成，不允许把知识检索逻辑直接写成固定 prompt 文案拼接在某个分支里。

### 15.4 direct 和 plan 的知识注入方式尽量统一

两种模式都应复用同一个知识检索服务和同一种 citation 数据结构。

### 15.5 引用字段必须可追踪

返回给前端的知识命中项，必须能够追踪到：

- 哪个知识库
- 哪个文档
- 哪个切片

否则后续无法做引用展示、点击回看和问题排查。

## 16. 推荐测试清单

后续代码实现完成后，至少应覆盖以下测试场景：

### 16.1 员工配置测试

1. 可保存多个有效知识库。
2. 不可保存不存在的知识库 ID。
3. 不可保存没有 processed 文档的知识库，或至少返回明确 warning。

### 16.2 direct response 测试

1. 员工绑定知识库且命中结果时，回答包含知识依据。
2. 员工未绑定知识库时，回答正常但无引用。
3. 员工绑定知识库但无命中时，回答正常并返回空引用。

### 16.3 plan 模式测试

1. planner 可生成带知识检索意图的步骤。
2. execute_plan 能执行这些步骤并注入检索结果。
3. 最终返回能包含引用来源。

### 16.4 异常测试

1. 单个知识库检索失败时，不影响其他知识库。
2. 火山接口超时或报错时，系统可降级。
3. 员工绑定历史失效知识库时，不会导致整个对话失败。

## 18. 推荐实施顺序

建议按以下顺序推进代码实现：

1. 先补员工保存时的 `knowledge_ids` 后端校验。
2. 再新增统一的员工知识检索服务层。
3. 先接 direct response，再接 plan mode。
4. 最后补回答引用返回结构和前端展示。

原因：

- 这样可以先打通最短链路。
- 之后再把同一套检索服务复用到 plan execution。
- 最后做引用展示时，数据结构已经稳定，不会反复返工。
