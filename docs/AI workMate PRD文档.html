1.0版本chat & mcp tool & account

本次新增 0107 版本需求，核心目标是将“硅基员工”从零散对话能力升级为可配置、可授权、可执行、可追踪的工作资源，形成从员工创建、工作台对话、计划审批、分步执行到任务复盘的完整闭环。

1. 核心功能点背景

1.1
企业对数字员工的诉求正在从单点问答走向可规模化的工作协作，希望 AI 不仅能回答问题，还能稳定承担资料检索与整理、分析报告生成、标准化文案产出、流程协助与执行跟踪等工作任务。
1.2
Merak 旨在将硅基员工产品化：让碳基员工能够像管理团队成员一样，完成硅基员工的角色定义、能力授权、使用协作、执行监督与结果复盘，沉淀可复用的组织级数字生产力资产。

2. 核心功能点目标

2.1
推动数字员工规模化落地，将分散的 AI 使用沉淀为可管理、可发布、可复用的“硅基员工资产”，降低组织侧重复配置与重复劳动成本。
2.2
建立从“选择硅基员工发起会话”到“计划生成、审批、分步执行、反馈修正、历史恢复”的完整任务闭环，提升复杂任务的交付效率与稳定性。
2.3
通过 To-do 与 Task Progress 建立过程可视化与结果可复盘能力，让多步骤任务具备更清晰的执行状态、责任归属和回溯路径。

6. 核心功能点通用规则与系统级说明

6.1
账号与登录态规则
规则项 内容
登录态失效规则 连续 12 小时无页面操作后，登录态自动失效并回到登录页，系统要求用户重新登录。
账号状态联动 账号被禁用、冻结或删除后，已登录中的会话在下一次接口请求时失效，并提示账号不可用。
6.2
会话定义与分组规则
规则项 内容
单聊会话 以“硅基员工 + 对话分组策略”为唯一范围；同一员工在同一时间窗口内的连续消息归属同一会话。
群聊会话 以“群组 + 模式类型 + 对话分组策略”为唯一范围；普通群聊、辩论模式、合作模式视为不同会话上下文。
时间窗口 连续超过 4 小时无消息时，新消息进入新会话；4 小时内默认延续上一会话。
刷新与切换 刷新后优先恢复最近一次未超时会话；切换员工或群组后进入目标对象最近一次会话，不共享原上下文。
清空历史 清空聊天记录只影响当前会话；清空后下次发送消息时，创建新的空会话。
6.3
状态、删除与恢复规则
对象 规则
Plan 支持待审批、已批准、已取消、执行中、已完成；重新生成计划后，旧版本保留为历史版本，新版本进入待审批。
Task / To-do 任务与 To-do 状态需联动；反馈重试时当前步骤保持进行中，终止任务时未开始步骤统一记为已取消。
历史恢复 恢复范围包括消息、计划审批卡、步骤结果卡、群组事件、To-do 状态与任务定位信息。
删除影响 删除某会话历史时，应同步删除关联消息、To-do、任务进度、步骤执行记录与临时执行上下文。
6.4
权限与异常规则
规则项 内容
能力边界 员工执行任务时仅能调用其被授权的 Core Skills、Extended Skills、MCP 与 Knowledge，不得跨员工越权调用。
配置变更生效 对硅基员工配置、Skill、Knowledge、MCP 的变更默认只影响后续新任务；运行中的任务继续使用启动时快照。
计划与执行异常 计划生成失败时保留用户原始输入；单步执行失败时至少提供重试与终止任务两个动作。
群组协作异常 合作模式下若某步骤负责人缺少所需能力授权，系统应中止后续流转，并提示具体缺失能力与责任节点。
6.5
配置对象新增、编辑、删除逻辑
对象 新增逻辑 编辑逻辑 删除逻辑
硅基员工 新建时先生成草稿或 Training 状态记录；未完成必填项或未发布前，不出现在可直接使用的员工列表中。 编辑已发布员工时，修改内容默认进入新的草稿版本；仅在用户完成 Onboard 或重新发布后，才对后续新会话和新任务生效。 删除前需校验是否存在未完成会话；若存在需提示处理影响。若存在运行中的任务，允许删除硅基员工本体，任务继续按启动时快照执行。删除后不再出现在员工列表，但历史会话、任务与执行记录保留用于复盘。
Skill 新建 Skill 时需完成名称、说明及必要配置；保存成功后进入 Skill 列表，并可被后续数字员工分配。 编辑 Skill 后，仅影响后续新的分配关系和新启动任务；已在运行中的任务继续使用启动时的 Skill 快照。 删除 Skill 前需展示其被哪些数字员工引用及影响范围；用户确认删除后，系统自动移除相关绑定。删除后历史任务中的 Skill 名称与调用痕迹保留。
MCP Toolset 新增 MCP 时需填写连接名称、服务地址及必要鉴权信息；支持测试连接，测试失败时保留填写内容并提示原因。 编辑 MCP 连接参数后，仅影响后续新的 Skill 调用与新任务执行；已启动任务继续沿用原执行快照，不中途切换连接。 删除 MCP 前需展示其被哪些 Skill 或数字员工间接引用及影响范围；用户确认删除后，系统自动移除相关绑定。删除后历史调用记录保留，不回写改动历史结果。
模型配置 新增模型时需完成提供商类型、模型名称、API Endpoint、API Key 等必填项；新建成功后进入模型列表，并可被数字员工后续选择使用。 编辑模型配置后，仅影响后续新会话或新任务；若当前模型正被运行中的任务使用，不中途切换其运行时模型。 删除模型前需校验是否仍被数字员工引用；若存在引用，需提示影响范围，用户确认删除后系统自动移除对应数字员工上的模型引用。删除不影响历史任务结果与审计记录。

7. 风险点、用户影响与缓解方案

风险点 典型场景 对用户的影响 缓解方案
工具 / MCP 调用超时 外部工具响应慢、网络抖动、第三方服务负载高。 用户看到步骤长时间无响应，误以为系统卡死；计划执行中断，任务完成时间不可控。 系统需提供超时提示、当前步骤重试入口与终止任务入口；超时不应吞掉原任务上下文，用户可在原会话中继续恢复执行。
模型响应失败 模型接口限流、报错、上下文超长或返回异常。 用户无法拿到计划或阶段结果，可能重复提交同一请求。 保留用户原始输入与当前计划状态；提示“生成失败 / 稍后重试”；对重复提交需避免生成多份并行任务。
历史恢复不完整 刷新页面、重新进入工作台、接口恢复失败。 用户看不到完整消息、To-do 或计划审批卡，影响继续执行和复盘。 恢复失败时优先恢复任务骨架信息；至少保留任务名称、当前步骤、状态与最近一次结果；前端需提供手动刷新与重新拉取入口。
配置变更与运行中任务不一致 员工、Skill、Knowledge、MCP、模型在任务运行期间被修改或删除。 用户会疑惑为什么当前任务仍在使用旧配置，或为什么新配置没有立即生效。 明确采用运行时快照机制；在任务详情或提示文案中说明“当前任务使用启动时配置，不随最新配置自动变更”。
多人协作链路中断 合作模式下某一位员工缺少权限、执行失败或交接异常。 任务停在中间步骤，用户无法判断责任节点与下一步动作。 系统需明确展示失败节点、责任员工、缺失能力与可选动作；至少支持重试当前节点、改派负责人或终止后续步骤。
误删除历史或配置对象 删除会话、删除员工、删除 Skill / MCP / 模型。 用户后续无法继续原任务，或误以为历史结果也被删除。 删除前展示影响范围与二次确认；历史任务结果、审计信息与关键执行记录应保留，不因配置对象删除而被抹除。

聊天对话文件上传 新增对话中的图片与文档上传能力，支持用户在发送消息前补充本地文件上下文。 覆盖 Add Photos & Files 按钮、本地文件选择、一次最多 10 个文件的数量校验、解析中状态展示、解析成功后的悬浮删除能力，以及超限失败提示。 Chat Workspace 输入区、上传文件卡片。 本期聚焦单次选择与上传态表达，不展开文件内容理解链路细节。

4. 功能明细

4.1
Knowledge Base
4.1.1
功能定位
Knowledge Base 用于承接数字员工可调用的知识来源管理能力，本期仅支持本地知识库导入与处理链路，围绕文档导入、切块、向量化结果展示等能力提供前端入口与状态表达。
4.1.2
核心流程
本地知识库主流程为创建知识库、导入文档、借用 Matrix 能力完成切块与向量化处理，并在详情页查看原始文档与切片结果。
4.1.3
页面与配置明细
页面/模块 功能说明 核心交互 备注
Knowledge Base 列表页 展示知识库列表，支持按名称搜索，并提供新建知识库入口。 搜索框按 Knowledge Base Name 检索；支持进入本地知识库详情。 本期以管理入口与列表展示为主。
创建知识库弹窗 支持创建本地知识库。 填写 Name、Description，用于创建本地知识库并进入后续导入流程。 本期不包含外部知识库连接入口。
Import Documents 用于向本地知识库导入原始文档并触发处理流程。 支持点击上传或拖拽上传；支持 PDF、TXT、DOCX、JPG、PNG；最多 10 个文件，单文件不超过 20 MB；点击 Save and Process 后进入处理。 导入后进入 Matrix 切块与向量化流程。
知识库详情页 包含 Original Docs 与 Slice Details 两个页签。 Original Docs 展示文档列表、状态、文件类型、上传时间与查看/删除动作；Slice Details 展示切片卡片与原文查看入口。 用于承接文档明细与切片结果查看。
数字员工创建页 / Knowledge 选择弹窗 用于为数字员工分配可用 Knowledge Base。 弹窗采用左侧 Knowledge Base 列表、右侧 Knowledge Base 详情的结构；仅展示包含至少一个 Processed 文档的 Knowledge Base；支持搜索、勾选、批量选择当前筛选结果并确认保存。 选择对象为 Knowledge Base，不下沉到文档粒度。
4.1.4
字段与状态规则
对象 字段/状态 规则 说明
本地知识库 Name / Description Name 为必填，最大 100 字；Description 为选填，最大 2000 字。 用于知识库基础信息管理。
文档状态 Pending / Processing / Processed / Failed 详情页需完整展示四种状态，并提供对应视觉区分。 用于体现导入后处理进度与异常状态。
数字员工知识绑定 Knowledge Base IDs / Processed 数字员工创建页保存的对象为 knowledge base id；仅允许选择并保存包含至少一个 Processed 文档的 Knowledge Base；支持多选并需去重保存。 用于限定数字员工可调用的知识范围。
4.1.5
业务规则与边界
规则项 内容
Matrix 能力 本地知识库导入文档后，切块与向量化处理能力借用 Matrix 能力完成；本期 PRD 关注前端入口、状态表达与结果展示，不展开 Matrix 内部算法细节。
权限范围 用户创建或导入的知识库默认仅供本人使用，共享、授权、团队级知识库管理不在本期范围内。
范围约束 本期不支持外部知识库连接、外部知识源配置与外部知识检索调用能力。
数字员工分配边界 数字员工创建页中只支持绑定 Knowledge Base，不下沉到知识文档粒度；仅包含至少一个 Processed 文档的 Knowledge Base 进入可选列表。
4.2
MCP
4.2.1
功能定位
用于承接 MCP 服务连接配置、连接管理与在 Skill 中的绑定表达，作为数字员工可调用外部能力的接入层。本期产品表达以 MCP Toolset 为主，即先配置可复用的 MCP 服务连接，再在 Skill 中选择绑定。
4.2.2
页面与配置明细
页面/模块 功能说明 核心交互 备注
MCP Toolsets 列表页 展示 MCP Toolset 列表，作为 Skill 可绑定的 MCP 服务连接管理入口。 支持按名称搜索；卡片展示名称、描述、场景（Domain）；支持点击卡片进入详情；支持直接在卡片上执行启用/停用与删除。 列表搜索范围仅限 Name，不支持按 Transport、Domain、Description 检索。
MCP Toolset 新建 / 详情抽屉 用于创建、查看、编辑单个 MCP Toolset 的连接配置。 新建时直接进入编辑态；查看已有 Toolset 时默认进入只读态，顶部提供 Edit 按钮切换编辑态；编辑项包括 Name、Version、Description、Source Type、Transport、Domain、Status、Config JSON；支持 Test Connection、Save Changes、Delete。 当前前端不展示 Toolset Key、Icon URL 等非必要字段。
Domain 分类 用于定义 MCP Toolset 的能力场景分类，便于用户识别和后续筛选扩展。 Domain 采用预置分类下拉单选；本期默认分类包括：浏览器自动化、搜索工具、交流协作工具、开发者工具、娱乐与多媒体、文件系统、金融、知识管理与记忆、位置服务、文化与艺术、学术研究、日程管理、其他。 本期按预置分类表达，不在前端开放自定义 Domain 分类能力。
Config JSON 区域 用于维护不同传输协议下的连接参数配置。 根据 Transport 自动回填默认 JSON 模板；STDIO 结构包含 command、args、env、timeout_seconds；HTTP / Streamable HTTP 结构包含 url、headers、timeout_seconds。 前端以 JSON 文本框形式直接编辑，不拆分为多字段表单。
SkillEditor / MCP Toolset Binding 用于在 Skill 中绑定单个或多个 MCP Toolset。 非 Workflow Skill 展示 MCP Toolset Binding 区域；查看态展示已绑定 Toolset 名称与描述；编辑态通过支持搜索的下拉复选框选择 MCP Toolset，选项展示为 Toolset 名称与一行描述，支持多选，也支持设置为空。 绑定对象可为单个或多个 MCP Toolset。
4.2.3
业务规则与边界
规则项 内容
权限与可见性 普通用户创建和维护的 MCP Toolset 默认仅供本人查看和使用；Admin 账号创建和维护的 MCP Toolset 对所有账号可查看和使用。
连接校验 Name、Description、Transport 为必填；保存时需校验 Config JSON 为合法 JSON；仅已保存的 MCP Toolset 支持 Test Connection；测试失败时需返回错误提示，不改变已保存配置。
Transport 规则 本期支持 STDIO、HTTP、Streamable HTTP 三种传输方式；切换 Transport 时前端需按协议自动回填默认配置模板，供用户继续编辑。
Domain 规则 Domain 使用系统预置分类；默认分类包括浏览器自动化、搜索工具、交流协作工具、开发者工具、娱乐与多媒体、文件系统、金融、知识管理与记忆、位置服务、文化与艺术、学术研究、日程管理、其他；本期不支持用户自定义新增分类。
绑定规则 Skill 与 MCP Toolset 为可选绑定关系；非 Workflow Skill 可配置绑定；一个 Skill 可绑定单个或多个 MCP Toolset；允许不绑定；变更绑定关系不修改 MCP Toolset 本身的定义。
状态规则 MCP Toolset 支持 Enabled / Disabled 状态切换；列表卡片可直接执行启用/停用；Disabled 状态仍保留配置记录，便于后续重新启用。
范围边界 本期聚焦 MCP 服务连接配置、查看、编辑、测试与 Skill 绑定表达。

Skill

功能定位
用于承接业务动作抽象、配置说明、以及与 MCP 的可选绑定关系，形成可供数字员工调用的技能单元；同时支持在数字员工创建页中进行 Skill 选择与分配。

页面与配置明细
页面/模块 功能说明 核心交互 备注
Skills 列表页 展示 Skill 列表，支持按名称搜索并进入详情配置页。 列表页以卡片方式展示 Skill 名称、说明、类型与启停状态，支持查看详情。 用于统一管理可分配 Skill。
SkillEditor 用于维护 Skill 的基础字段、说明文案与 MCP 绑定表达。 支持编辑名称、描述、类型与 MCP Binding 区域等配置项。 本期重点是配置表达与绑定关系展示。
数字员工创建页 / Skill 选择弹窗 用于为数字员工分配可用 Skill。 弹窗采用左侧 Skill 列表、右侧 Skill 详情与启用开关的结构；支持搜索、切换当前 Skill、单个启用与批量勾选当前筛选结果。 保存对象为 skill key，创建页需展示已选 Skill 卡片并支持再次编辑或移除。

业务规则与边界
规则项 内容
Skill 规则 Skill 支持在数字员工创建页中按 skill key 分配；同一数字员工可分配多个 Skill；保存时需按 skill key 去重。
权限与可见性 普通用户创建和配置的 Skill 默认仅供本人查看和使用；Admin 账号创建和配置的 Skill 对所有账号可查看和使用。

4.4
模型配置
4.4.1
功能定位
用于承接模型连接信息的前端管理能力，支持用户维护模型列表、编辑基础连接参数、设置单个激活模型，并通过 Private / Public 表达模型的可见范围。
4.4.2
页面与配置明细
页面/模块 功能说明 核心交互 备注
Model Configuration 作为模型连接管理入口，展示当前已配置模型列表。 列表展示 Name、Provider、Endpoint、Public、Updated；支持 Add Model、Edit、Delete，并支持在数字员工配置中选择该模型。 页面已在 Settings > Model Configuration 下独立路由落地。
Create / Edit Drawer 用于创建与编辑单个模型连接配置。 抽屉中支持填写 Model Name、Provider Type、API Endpoint、API Key；支持切换 Public；Public 打开后需勾选确认项；支持 Cancel、Create Model / Save Changes。 API Key 支持 Show / Hide 切换。
Provider Type 用于选择模型连接的提供商兼容类型。 本期预置下拉选项仅包含：Open AI Compatible、Azure OpenAI Compatible。 本期不支持自定义新增 Provider Type，也不包含其他兼容类型选项。
模型选择与可用范围 用于维护可被数字员工选择的模型连接。 模型保存后进入模型列表，数字员工可在创建或编辑时按需选择具体模型；系统不维护全局唯一默认模型。 模型是否实际生效，以数字员工配置和运行时接入能力为准。

业务规则与边界
规则项 内容
配置规则 Model Name、API Endpoint 为必填；API Key 当前前端可为空保存；Provider Type 为预置下拉选择，默认值为 Open AI Compatible；API Endpoint 默认值为 https://api.example.com/v1。
公开范围规则 模型默认以 Private 保存；切换为 Public 时需额外勾选确认项，明确该模型将对当前组织内所有成员可用。
选择规则 模型保存后进入可选范围，由数字员工在创建或编辑时自行选择；未被数字员工选择的模型仅作为候选配置存在。
存储规则 当前模型配置数据保存在浏览器 localStorage 中；首次进入页面时会以默认示例模型初始化，用于前端演示和交互验证。
前后端边界 当前 Model Configuration 页面尚未对接独立后端模型配置接口；页面中的新增、编辑、删除仅影响前端本地存储与数字员工可选项表达。后端运行时模型仍基于环境变量读取，当前实际使用的是 Azure OpenAI 或 OpenAI 的环境配置，不直接消费该页面数据。
4.5
聊天对话文件上传
4.5.1
功能定位
用于承接聊天工作台中用户发送前的本地文件补充能力，使用户可在对话上下文中附带图片或文档作为输入材料，并在上传解析阶段获得明确状态反馈。
4.5.2
页面与交互明细
页面/模块 功能说明 核心交互 备注
Chat Workspace / Add Photos & Files 作为聊天输入区的文件补充入口，支持用户从本地选择图片或文档文件。 点击 Add Photos & Files 后打开本地文件选择器；支持用户一次性选择多个文件，并将所选文件插入输入区上方的文件列表。 按钮文案固定为 Add Photos & Files。
文件数量校验 用于限制单次选择文件数量，避免一次上传过多文件造成交互混乱与解析压力。 单次从本地选择文件时最多允许选择 10 个；若选择数量超过 10 个，则本次选择失败，且需直接提示错误文案：You may only upload 10 files at a time. 超限场景下，本次所选文件不进入待解析列表。
文件解析中状态 用于表达文件已被选中并正在被系统解析。 文件进入列表后默认展示加载符，表示当前处于解析中；解析完成前文件不可作为稳定输入结果展示。 本期重点是上传后状态可见，不展开解析进度百分比。
解析成功态与删除 用于表达文件已可被对话使用，并支持用户移除不再需要的文件。 解析成功后移除加载中状态；当鼠标悬浮在已解析成功的文件卡片上时，展示删除入口，支持删除当前文件。 删除仅作用于当前输入区已选文件，不影响本地原文件。
4.5.3
业务规则与边界
规则项 内容
文件类型范围 本期仅支持用户在聊天中上传图片与文档文件，作为对话输入材料使用；不展开音视频等其他文件类型能力。
数量限制 一次本地文件选择最多 10 个；超过 10 个时，本次选择整体失败，不做部分接收，并提示固定错误文案：You may only upload 10 files at a time.
状态规则 文件选中后先进入解析中状态并展示加载符；解析成功后不再显示加载中状态；本期仅要求明确表达解析中与解析成功两类前端状态。
删除规则 仅解析成功后的文件支持在鼠标悬浮时显示删除入口；删除后文件立即从当前上传列表移除，不保留占位。
范围边界 本期 PRD 聚焦聊天输入区的上传入口、数量校验、状态表达与删除交互，不展开服务端解析实现、文件摘要生成或跨会话持久化规则。
4.6
配置对象新增、编辑、删除逻辑
对象 新增逻辑 编辑逻辑 删除逻辑
数字员工 新增数字员工时，需先完成基础信息、Knowledge/Skill 分配及必要配置；保存成功后形成可继续编辑的配置记录，发布后才进入可用范围。 编辑数字员工配置时，系统需保留原有已发布版本，修改内容仅对后续新任务生效；运行中的任务继续使用启动时快照。 删除数字员工前需校验是否存在历史会话或有效绑定，并提示相关影响；若存在运行中任务，允许删除数字员工本体，运行中任务继续按启动快照执行。删除后不再允许被新会话选择，但历史会话和任务记录保留。
Skill 新增 Skill 时校验名称、描述、配置项及 MCP 绑定信息；保存成功后可进入 Skill 列表，并支持后续分配给数字员工。 编辑 Skill 后，仅影响后续新分配与新任务；若 Skill 已被多个数字员工使用，系统需在保存前提示影响范围。 删除 Skill 前需展示被引用的数字员工与绑定数量；用户确认删除后，系统自动解除相关绑定。删除不抹除历史执行记录。
MCP Toolset 新增 MCP 时需完成连接信息与鉴权配置，并支持测试连接；保存失败时保留已填内容并给出明确原因。 编辑 MCP 连接参数或绑定信息后，仅影响后续新的调用链路；运行中的任务不应动态切换到新连接。 删除 MCP 前需校验其是否仍被 Skill 引用；若存在引用，需提示失效关系，用户确认删除后系统自动解除相关绑定。
模型配置 新增模型时需校验必填字段完整性；保存成功后进入模型列表，并可被数字员工后续选择使用。 编辑模型后，仅影响后续新会话与新任务；对于运行中的任务，保留当次启动时使用的模型配置快照。 删除模型前需校验是否仍被数字员工引用；若存在引用，需提示影响范围，用户确认删除后系统自动移除对应数字员工上的模型引用。
聊天上传文件 用户通过 Add Photos & Files 选择文件后，系统立即创建当前输入态下的文件项并进入解析中状态；若单次选择超过 10 个，则本次新增失败并展示错误提示，不创建任何文件项。 文件在解析中阶段持续展示加载状态；解析成功后切换为稳定展示态，可继续参与当前消息发送流程。 删除当前输入区文件时，仅移除本次会话输入中的挂载关系，不删除本地源文件，也不回写历史消息内容。

0326 版本 PRD

本次新增 0326 版本需求，核心补充聊天工作台中的单聊对话逻辑与不同群聊模式下的对话逻辑，统一定义会话、计划审批、执行反馈、群聊分发、辩论模式与合作模式的产品交互和规则边界。

1. 背景

1.1
现有需求对单聊场景下的完整对话逻辑定义不够充分，需要补齐从用户提问、计划生成、计划审批、分步执行、反馈修正到历史恢复的标准交互链路。
1.2
现有需求对群聊场景下的不同对话模式定义不完整，需要明确普通群聊、辩论模式、合作模式三种协作路径及其消息表现、参与成员选择和执行规则。
1.3
为支撑后续审批流、任务追踪和协作能力扩展，需要统一聊天工作台在单聊与群聊中的状态表达、消息类型和历史恢复逻辑。

2. 本期范围

模块 本期目标 本期范围 关键页面/对象 备注
单聊工作台 建立单个硅基员工的一对一对话闭环。 覆盖选择员工、历史恢复、计划生成、审批执行、步骤反馈、To-do 联动和结果交付。 Chat Workspace 单聊模式、计划审批卡、步骤结果卡、To-do 面板。 强调“先计划、后执行”的复杂任务交互。

功能定位

核心流程

4. 群聊对话逻辑

4.1
群聊模式总览
模式 适用场景 核心机制 主要输出
普通群聊 用户希望获得 1 名或多名成员的直接回复。 系统按意图自动选择回复成员，或根据 @ 点名路由到指定成员。 成员直接回复消息、系统路由提示。
辩论模式 用户希望比较观点、听取不同立场并获得综合结论。 系统选择参与者、按轮次发言、最后生成主持总结。 轮次消息、辩论总结。
合作模式 用户希望完成一个需要多角色分工的复杂任务。 系统自动分配成员，先生成协作计划，审批后按顺序接力执行。 协作计划审批卡、接力结果、最终汇总。
4.2
普通群聊
环节 逻辑说明 规则
消息发送 用户在群中发送消息，可直接输入文本，也可通过 @ 触发成员选择面板。 @ 单人表示点名该成员；@All 表示全员收到点名。
成员分发 若用户未点名，系统根据消息意图自动匹配最合适的 1 至 2 名成员进行回复。 系统会插入一条路由提示消息，说明已分配给哪些成员。
成员回复 每个被选中的成员只代表自己回复，不代替其他成员发言。 回复消息需带成员身份标识和头像。
历史恢复 群聊消息刷新后仍可恢复，包括用户消息、系统路由消息和成员回复。 会话维度为 group id + 时间分组策略。
4.3
辩论模式
环节 逻辑说明 规则
模式开启 用户在群聊顶部切换为辩论模式，并可设置辩论轮数。 默认轮数为 2，支持按产品配置限制最大轮数。
参与者选择 系统优先使用被 @ 点名的成员参与辩论；若未点名，则自动挑选最适合主题的成员。 参与成员应至少为 2 人。
分轮发言 第一轮各成员陈述核心观点；后续轮次针对其他成员观点进行补充或反驳。 每条辩论消息需标记轮次和阶段。
主持总结 辩论结束后由系统或主持成员输出综合结论。 总结需给出最终推荐结论与主要理由。
4.4
合作模式
环节 逻辑说明 规则
模式开启 用户切换为合作模式并输入任务目标、约束和期望产物。 合作模式默认面向复杂任务，不适合简单问答。
协作计划生成 系统根据群成员角色、人设、可用 MCP / Skill / Knowledge 自动选择参与成员，并生成协作计划审批卡。 计划需标明步骤编号、负责人、输入来源、预计输出。
计划审批 用户可批准执行，或提交调整意见重新生成协作计划。 未经批准不得进入协作执行阶段。
接力执行 步骤负责人执行后，系统将结果自动交接给下一位成员继续处理。 消息流需展示系统交接提示、当前负责人、交接摘要。
结果汇总 最后一位成员或系统协调者输出最终交付结果。 最终消息需可直接作为面向用户的完整结果。

5. 通用规则与边界

规则项 内容
会话恢复 单聊与群聊均需支持刷新后恢复历史消息。群聊历史除消息文本外，还需保留模式类型、发言成员、步骤阶段和系统路由信息。
消息类型 消息类型至少包括：用户消息、助手文本、系统路由消息、计划审批卡、步骤结果卡、辩论轮次消息、辩论总结消息、合作模式交接消息、合作模式最终汇总消息。
模式切换 群聊支持在普通群聊、辩论模式、合作模式之间切换。切换模式只影响后续新消息处理逻辑，不应篡改历史消息的模式标识。
能力边界 在群聊合作模式下，每个参与员工只能调用其被授权的 MCP、Core Skills、Extended Skills 与 Knowledge；系统不得跨员工越权调用其他成员能力。
异常处理 计划生成失败、单步执行失败、协作交接失败、模式执行中切换群组等异常场景，均需提供清晰的错误提示与可恢复动作，例如重试、终止、返回 Idle 状态。
范围边界 0326 版本 PRD 聚焦对话逻辑、状态表达和交互闭环，不扩展组织级权限体系、复杂协作审计策略和群聊外的广场/市场能力。

6. 风险点、用户影响与缓解方案

风险点 典型场景 对用户的影响 缓解方案
计划生成耗时过长或失败 复杂请求过长、模型负载高、上下文过大。 用户不知道当前是“正在规划”还是“已卡死”，可能反复发送同一需求。 在计划生成阶段展示明确的处理中状态；超时后保留原始输入并提示重试；避免重复触发多份并行计划。
步骤执行超时 单步调用搜索、浏览器、MCP 或多轮模型推理时间过长。 用户感知系统卡顿，无法判断当前执行到哪一步。 在消息流和 To-do 中同步当前步骤状态；超过阈值需提示“执行超时”；支持重试当前步骤、跳过或终止任务。
群聊路由错误 普通群聊自动分发给了不合适的成员，或遗漏更适合的成员。 用户收到低质量回复，降低对自动选人的信任。 系统路由消息需可解释；允许用户通过 @ 点名修正；对自动分发结果保留人工覆盖能力。
辩论模式失控 成员观点重复、轮次过多、总结无法收束。 用户看到大量冗余消息，信息密度下降，难以得到结论。 限制轮次上限；要求每轮消息有阶段标记；最后必须输出结构化总结与明确结论，不可只停留在观点罗列。
合作模式交接失败 上一步结果格式异常、下一位成员缺少上下文、负责人能力不足。 任务中断，用户只能看到部分产物，无法继续推进。 系统需展示交接摘要、当前负责人和失败节点；失败后支持重试交接、改派负责人或回退到上一步重新产出。
刷新后恢复错位 群聊模式切换频繁、消息类型复杂、历史状态未完整恢复。 用户无法区分当前会话属于普通群聊、辩论还是合作模式，影响继续操作。 恢复时需带回模式标识、轮次、步骤阶段和系统事件；恢复失败时至少展示最近一次任务模式和状态摘要。

0327 版本 PRD

本次新增 0327 版本需求，核心目标是在既有单聊、普通群聊、辩论模式与合作模式基础上，进一步明确“单人 Plan”和“多人协作”之间的适用边界、路由原则与交互表达，避免复杂任务被误判为多人任务，或多人任务被错误压缩为单人执行。

1. 核心概念定义

概念 定义 核心价值 不应误解为
Direct 不需要系统级显式规划，直接由一个数字员工完成处理。 响应快、交互轻、成本低。 不等于只能纯文字回答；员工内部仍可调用能力。
单人 Plan 由一个数字员工先对复杂任务进行内部或系统级步骤拆解，再按顺序执行并产出统一交付。 覆盖“复杂但不需要多人分工”的中间地带。 不等于多人协作的降级版。
Collaboration 多个数字员工围绕同一任务按步骤分工推进，存在上下游交接关系。 适合跨角色、多阶段、强依赖任务。 不等于所有复杂任务都要走 collaboration。
Debate 多个数字员工围绕同一问题输出不同观点，再由系统或指定员工总结。 适合策略评估、方案比较、视角碰撞。 不适合流程型接力任务。

2. 为什么一定要有单人 Plan

问题 如果没有单人 Plan 带来的问题 单人 Plan 的价值
复杂任务只能 direct 或多人二选一 系统要么直接回答，要么强行拉多人协作。 前者容易答乱，后者成本过高。 补足“复杂但不需要多人”的中间能力层。
用户需要统一口径 多人拆开执行后再拼接。 风格不一致、术语不统一、结论可能冲突。 由一个数字员工统一完成，保证口径一致。
任务存在顺序依赖 直接回答无法显式控制先后步骤。 结果容易遗漏中间判断和关键检查点。 通过 Plan 保证先分析、再归纳、再输出。
交互成本控制 多人协作链路默认更长。 更多 token、更多切换、更多失败点。 在单员工范围内完成复杂任务，更高效稳定。
用户心智 用户每次都看到多人参与。 会感知系统冗长，削弱“负责人到底”的体验。 单人 Plan 更符合“一个负责人到底”的工作心智。

3. 典型用户场景

场景类型 用户示例 适合单人 Plan 的原因 为什么不适合多人
写方案类 帮我做一个竞品分析框架，再给结论，再整理成汇报结构。 先分析、再归纳、再组织表达，流程复杂但责任主体可为一个分析型员工。 用户要的是统一交付，不是多人各写一段后再拼接。
内容生产类 先帮我想咖啡馆海报方向，再写提示词，再决定要不要生图。 步骤有依赖关系，但整体风格需要由同一创意员工统一把控。 多人参与容易造成风格分散、表达不统一。
研究归纳类 先梳理 OpenClaw 的定位，再分析竞品，再给合作建议。 是典型研究链路，一个研究型员工即可完成闭环。 多人拆分后容易出现信息重复、口径冲突、结论不一致。
单职能深任务 帮我优化一个页面文案，先找问题，再给改法，再给最终版本。 这是完整诊断到输出链路，适合由同一个文案或运营员工独立完成。 设计、产品、运营都参与会导致协作成本远高于收益。
工具链串行任务 先搜集资料，再整理重点，再输出总结。 虽然中间会调用搜索、知识库、技能，但这些只是同一员工内部能力调用。 工具调用不等于角色切换，不应因此强制多人化。

4. 为什么复杂不等于多人

复杂度类型 定义 适合的解决方式 典型例子
流程复杂 任务步骤多、存在先后顺序、需要中间检查点。 优先考虑单人 Plan。 先分析，再归纳，再写结论。
角色复杂 需要不同专业角色分别负责不同子任务。 优先考虑 Collaboration。 产品方案 + 设计建议 + 运营落地。
视角复杂 需要不同立场、不同角色给出对立或补充观点。 优先考虑 Debate。 两个方案优劣比较、战略选择讨论。

5. 为什么不能默认都用多人完成

问题项 多人默认化后的结果 业务影响
延迟更高 多人链路天然带来上下文传递、等待、汇总与角色切换。 整体响应变慢，简单复杂任务都被重型化。
成本更高 需要更多模型调用、更多上下文拼接、更多协调 prompt。 token 消耗增加，链路更长，失败点更多。
结果不一致 多人各自理解任务，容易出现术语、风格、结论不统一。 尤其影响方案类、文案类、视觉类交付。
责任边界模糊 用户难以判断谁对最终结果负责。 不符合“一个负责人到底”的工作心智。
用户体验更重 用户频繁看到协作过程和中间状态。 会觉得系统在“表演协作”，而不是高效完成任务。

6. 什么时候才应该多人完成

触发条件 说明 推荐模式 示例
明显跨职能 任务天然需要不同职能员工分别完成不同部分。 Collaboration 产品方案 + 设计建议 + 运营落地。
明显需要不同视角 任务重点在于比较不同观点，而不是顺序执行。 Debate 路线选择、方案优劣比较、战略讨论。
子任务可独立拆分 多个子任务之间可分配给不同角色，且合并后价值更高。 Collaboration A 调研，B 整理，C 汇报。
用户明确要求多角色参与 用户希望看到不同角色共同参与或评审。 Collaboration / Debate 让产品、设计、运营一起评审这个方案。
单人执行会明显丢专业性 任务需要多专业背景共同参与才可靠。 Collaboration 法律审查 + 财务测算 + 品牌表达。

7. 路由判断原则

判断顺序 问题 是 否
第一步 是否需要澄清信息后才能继续？ 进入 Clarify 继续下一步判断
第二步 任务是否需要显式步骤拆解？ 进入 Plan 判断 进入 Direct
第三步 任务是否需要多个角色分别负责？ 进入 Collaboration 进入单人 Plan
第四步 任务是否更适合多观点碰撞而非串行执行？ 进入 Debate 保留原判断

8. 模式适用矩阵

模式 是否多步骤 是否多人 是否强调统一口径 适合任务
Direct 否或极弱 否 是 简单问答、轻量生成、即时建议
单人 Plan 是 否 强 复杂但单角色可闭环的任务

9. 交互设计原则

场景 用户应感知到什么 不应感知到什么
Direct 快速得到结果。 不应被复杂计划审批打断。
单人 Plan 任务被有条理地拆解和完成，必要时可展示计划与执行过程。 不应被强行多人化。
Single Assignee 群里由最适合的员工负责回复，其他成员不制造噪音。 不应所有人都同步发言。
Collaboration 看到分工、接力、交接与最终汇总。 不应看不到负责人和阶段信息。
Debate 看到不同观点及最终总结。 不应被错误包装成串行执行流程。

10. 通用规则与边界

规则项 内容
执行主体 系统中真正的执行主体与发言主体始终是数字员工。Skill、Knowledge、搜索、浏览器、生图能力均属于数字员工内部可调用能力，不作为独立发言主体存在。
单人 Plan 定位 单人 Plan 用于处理“流程复杂但角色不复杂”的任务，不以多人参与为前提。
多人触发原则 只有在角色分工、多视角讨论、用户明确要求多人参与或单人明显不足以保证专业性的场景下，才进入 Collaboration 或 Debate。
统一口径原则 对于方案类、文案类、视觉方向类等强调统一表达的任务，默认优先评估单人 Plan，而非直接多人协作。
交互重量级控制 系统应尽量以最轻的合适模式完成任务，避免将简单任务复杂化、将复杂任务无差别多人化。

11. 风险点、用户影响与缓解方案

风险点 典型场景 对用户的影响 缓解方案
复杂任务被误判为多人协作 本质上可由单一员工完成，但系统错误触发 Collaboration。 用户感知链路变重、耗时更长、成本更高，且结果口径可能不统一。 路由优先判断是否只是“流程复杂”；仅在明确跨角色分工时进入 Collaboration；对方案类、文案类、研究类任务优先评估单人 Plan。
多人任务被误压缩为单人执行 任务实际需要多职能输入，但系统只分配给一个员工。 结果专业性不足，关键视角缺失，用户对最终结果可靠性存疑。 当任务存在明显跨职能、强专业边界或用户明确要求多人参与时，应强制进入 Collaboration 或 Debate。
将工具调用误当作多人协作 单个员工在执行中调用搜索、知识库、浏览器或生图能力。 用户误以为系统引入了多个执行主体，造成心智混乱。 文案和交互上明确“执行主体始终是数字员工，工具仅为其内部能力”；不要把工具返回包装成独立成员发言。
模式切换频繁导致心智断裂 同一任务在 Direct、单人 Plan、Debate、Collaboration 之间反复切换。 用户不清楚当前系统为什么这样执行，也不清楚谁对结果负责。 模式一旦进入执行阶段，应尽量稳定；若需要切换模式，需先给出原因说明，并由用户确认。
责任边界不清 多人模式下没有明确负责人，或总结输出者不清晰。 用户无法判断谁应对最终交付负责，影响信任和复盘。 单人 Plan 默认一个员工负责到底；Collaboration 需明确步骤负责人和最终汇总负责人；Debate 需明确主持总结角色。
用户对系统能力预期过高 用户看到多人或计划化流程后，默认认为结果一定更准确。 一旦输出质量一般，会放大失望感与不信任。 在 PRD 和产品文案中明确：多人不天然优于单人，系统目标是以最轻且最合适的模式完成任务，而非默认追求复杂编排。

0626 合同审查智能体 PRD

本次新增合同审查智能体需求，核心目标是将合同、招投标文件、广告文案等法律文件的风险审查，从人工逐条检查升级为可上传、可审查、可对比、可修订、可沉淀规则的智能工作流，帮助用户快速发现法律风险、定位原文并生成可操作的修改建议。

1. 背景

1.1
合同类文件存在条款多、版本多、风险点分散、人工审查耗时长等问题，法务或业务人员需要在较短时间内完成风险定位、主体核验、条款修改与结果留痕。
1.2
当前业务场景已具备合同审查智能体原型，包括法律文件审查、对比审查、风险分级、审查结果展示、知识库与规则库等页面能力，适合作为 WorkMate 垂直智能体的首批落地样板。
1.3
本期需将合同审查能力产品化，明确上传入口、审查链路、审查清单、规则配置、修订动作、历史记录与人工确认边界，支撑后续扩展到人资、采购、法务等更多业务智能体。

2. 本期目标

2.1
支持用户上传单份法律文件进行审查，覆盖合同、招投标文件、广告文案等文件类型，输出风险等级、风险点、原文定位与修改建议。
2.2
支持对比审查，允许用户上传待审文档与标准文档，识别两份文档在条款、格式、主体、金额、期限、义务、责任等方面的差异。
2.3
建立合同审查知识库与规则库，支持文件审查清单、审查规则分组、自定义规则、新建规则、规则文档解析和规则详情查看。
2.4
形成审查结果闭环，支持风险筛选、风险详情、定位原文、编辑建议、一键修订、接受建议并添加修订、下载结果与历史记录查看。

3. 本期范围

模块 本期目标 本期范围 关键页面/对象 权限与边界
文件审查 完成单份法律文件的智能风险审查。 覆盖文件上传、格式校验、剩余额度展示、开始审查、审查进度、结果生成与历史记录。 法律文件审查首页、上传区、历史面板、审查结果页。 单个合同文件字数不超过 20 万字，格式支持 PDF / DOC / DOCX。
对比审查 完成待审文档与标准文档的差异识别。 覆盖双文件上传、标准文档说明、差异识别、格式要求提示、结果输出。 对比审查页、待审文档上传区、标准文档上传区、对比结果。 本期聚焦文档差异与风险提示，不直接替代法律结论。
审查结果 以可读、可定位、可操作方式展示审查结果。 覆盖合同概览、审查清单、审查结果三步进度，高/中/低风险与通过项统计，风险详情卡片与原文定位。 合同概览、审查清单、审查结果、风险点卡片、原文编辑器。 高风险建议默认需要用户确认后再执行修订。
知识库 沉淀审查清单与业务审查标准。 覆盖文件审查清单列表、新建清单、规则数量、最后修改时间、搜索与空状态。 知识库、文件审查清单、清单列表、新建清单。 清单可作为不同文件类型或业务场景的审查入口。
审查规则库 支持规则配置、规则解析和规则复用。 覆盖规则分组、自定义场景、买卖合同等默认分类、新建规则、解析规则文档、规则详情、编辑规则。 审查规则库、规则分组、规则列表、规则详情。 规则更新后需记录修改时间，后续可扩展审批与版本管理。

4. 核心业务链路

链路阶段 用户动作 系统处理 输出结果
1. 文件接入 用户选择法律文件审查或对比审查，并上传 PDF / DOC / DOCX 文件。 校验文件格式、字数上限、审查额度，创建审查任务并进入解析队列。 上传成功状态、审查任务 ID、历史记录入口。
2. 文档解析 用户等待系统处理。 解析正文、标题、表格、签署页、附件、水印和关键字段，生成合同结构化视图。 合同概览、主体信息、条款分段、关键字段。
3. 规则匹配 用户可选择默认规则或自定义审查清单。 按合同类型匹配审查清单与审查规则，执行风险识别、主体审查和对话审查。 审查清单执行结果、高/中/低风险统计、通过项统计。
4. 风险生成 用户查看风险点。 生成风险说明、合同原文、建议修订条款，并关联原文位置。 风险卡片、原文定位、修改建议。
5. 修订确认 用户编辑建议、添加批注、接受建议并添加修订或一键修订。 将建议转为文档修订痕迹，保留原文、建议、用户动作与审计记录。 修订后文档、批注记录、审查日志。
6. 结果沉淀 用户下载结果或返回历史记录。 保存审查结果、风险分类、规则命中、用户采纳情况。 历史审查记录、可复用规则样本、后续优化数据。

5. 功能明细

5.1
法律文件审查首页
页面需展示产品标题“法律文件审查，智能识别法律风险”、说明文案、法律文件审查 / 对比审查切换、文件上传区、审查剩余额度、历史记录入口和法律文件审查知识库入口。上传区支持点击或拖拽上传，未上传时展示空态，上传后展示文件信息与开始审查按钮。
5.2
对比审查
对比审查需提供待审文档与标准文档两个上传区域，说明待审文档用于与标准文档比对差异，标准文档用于识别差异点。两份文件均上传完成后，开始审查按钮可用。
5.3
审查过程与三步进度
审查任务进入结果页后，顶部展示合同概览、审查清单、审查结果三个阶段。已完成阶段高亮，当前阶段展示处理中或完成状态，用户可理解当前任务所处位置。
5.4
风险审查结果
结果页按风险审查、主体审查、对话审查三个页签组织内容。风险审查页需展示高风险、中风险、低风险、通过项数量，并以卡片形式列出审查项、风险等级、风险说明、合同原文、建议修订条款、添加批注和接受建议并添加修订按钮。
5.5
原文定位与文档修订
当用户点击定位原文时，左侧文档编辑区应滚动并高亮对应合同原文。用户点击接受建议并添加修订后，系统将建议条款写入文档修订结果，并提示“已找到相似原文，建议划选准确后点击接受进行更正”。
5.6
知识库与审查清单
知识库页包含文件审查清单和审查规则库两个入口。文件审查清单列表需展示清单名称、规则数量、最后修改时间、操作、新建清单、搜索和空状态。
5.7
审查规则库
审查规则库左侧展示规则分组，包括自定义场景、买卖合同、供用电水气热力合同、赠与合同、借款合同、租赁合同、融资租赁合同、承揽合同、建设工程合同、运输合同、技术合同、保管合同、仓储合同等。中间区域展示规则列表、搜索、新建规则和解析规则文档；右侧展示规则详情和编辑入口。

7. 通用规则与系统级说明

7.1
合同审查结果需明确声明“服务生成的所有内容均由人工智能模型生成，其生成内容的准确性和完整性无法保证，不能代表我们的态度和观点”。
7.2
风险等级至少包含高风险、中风险、低风险、通过四类，风险结果需支持按等级筛选和统计。
7.3
一键修订和接受建议并添加修订均不得自动覆盖原文，需保留原文、建议文本和修订痕迹，便于用户复核。
7.4
审查规则库中新增或解析生成的规则需可追溯来源，后续版本应支持规则启停、版本管理和发布前评测。
7.5
历史记录需区分文件审查与对比审查，支持按名称搜索，并展示审查任务的最近状态。

8. 风险点、用户影响与缓解方案

风险点 典型场景 对用户的影响 缓解方案
法律风险误判或漏判 模型对复杂条款、行业特定条款或上下文关系理解不足。 用户可能误以为审查结果等同法律意见，导致决策风险。 明确 AI 免责声明；高风险建议保留人工确认；提供原文定位、规则命中和建议依据，便于复核。
原文定位不准确 PDF 解析、跨页段落、表格条款或扫描件 OCR 结果存在偏差。 用户无法快速验证风险来源，影响修订效率。 定位失败时展示相似原文候选；允许用户手动划选准确文本后再接受修订。
规则配置不当 用户新增规则表达不清、规则冲突或适用合同类型错误。 审查结果不稳定，可能出现重复风险或错误建议。 规则保存前做必填项校验；解析规则文档后进入待确认状态；后续支持规则测试样本。
用户误触一键修订 用户未逐条确认即批量采纳建议。 合同文本可能产生不符合真实谈判意图的修改。 一键修订前展示二次确认；高风险或主体类条款默认不自动批量采纳。
文件隐私与敏感信息泄露 合同包含客户名称、金额、人员信息、商业机密等敏感内容。 用户对上传和审查过程的安全性产生顾虑。 限制文件可见范围；记录下载和修订审计；后续结合敏感信息识别与脱敏能力。
